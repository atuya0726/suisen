# 日次の収集

著名人や大学の教員が「薦めた」と文字で確認できる本を、出典つきで足す。1回の実行で、調査、取り込み、確認、公開、記録、報告までを終える。

状態は `docs/operations.md`（優先順位、継続して見る一覧、ログ）と `data/research/checked-urls.json`（調査済み URL の台帳）にある。データの決まりは `CLAUDE.md` §3 と §7。このスキルは手順と判断基準だけを持つ。

## 無人実行のとき

スケジュール実行では、途中で誰も答えない。次を守る。

- ユーザーに質問しない。判断がつかないものは取り込まず、報告に書く。
- 迷ったら載せない。誤った紐付け（その人が薦めていない本）が、誰にも止められず本番に出るため。
- 最後に必ず Discord へ報告する。何も足さなかった回も、その理由を送る。

## 1. 始める前の確認

1. `docs/operations.md` を読む。
2. `git status --short` を見る。未コミットの変更があれば、ユーザーの作業中かもしれないので、触らずに中止して報告する。
3. 本番の生存確認をする。`https://suisen.page/` と、人物ページを1つ取得し、200 で本文が返ることを見る。落ちていたら、収集より先に原因を調べて報告する。

## 2. 調べる対象を決める

`docs/operations.md` の「収集の優先順位」の順に、その日の上限まで選ぶ。

- 台帳で `result` が `adopted` / `rejected` / `pending` の URL は開かない。`candidate` は候補、`index` は一覧ページ（新着の確認に使う）。
- **1日の上限**: 調査役は同時に3つまで、合計で5つまで。足す推薦は150件まで。1つの大学は10人まで。
- 新着が無く、候補も尽きた項目は飛ばす。全部尽きていたら「新しい連載・企画の発見」に1つだけ調査役を出す。

## 3. 調べる

調査は Sonnet のサブエージェントに任せる（ユーザーの全体ルール）。一覧ページに必要な情報が全部載っている出典（北海道大学など）は、調査役を使わずスクリプトで取る。

調査役への依頼には、次を必ず入れる。

- **対象の一覧ページか記事の URL**。人を決めて記事を探させない（時間がかかり、外れが多い）。
- **道具の上限**（ツール呼び出し 40〜45回）と、取得を拒否されたら粘らずに諦めること。
- 記事は `curl -sL -A "Mozilla/5.0" URL` で生の HTML を取り、**本文を読んで**確かめること。記事末の書誌の欄だけで判断しない。
- 拾うのは、本人が薦めている・選んでいる・影響を受けたと語っている本だけ。自著、自分が訳した本、出演作の原作など宣伝対象の本、話題に出ただけの本は除く。対談や複数人の企画は、誰がどの本かがはっきりしないものを載せない。
- **推薦理由や記事の内容を要約しない**。記録するのは「誰が・どの本を・どの記事で薦めたか」だけ。
- **ISBN は調べさせない**。ページに書かれていれば写す。書名は本題だけにして、副題は `subtitle`、版・刊行年・叢書名は `edition` に書く。著者名が分からない本は載せない。
- 漫画・全集など巻の指定がないシリーズは、書名をそのまま書いて `edition` を「シリーズ」にする。上下巻は書名に「上」を付ける。日本語版でない洋書、DVD は除く。
- 有料・会員限定（無料登録が必要なものも含む）の記事は使わない。
- 公開日は記事に出ている日付。分からなければ省く（推測で埋めない）。
- 人物の `title` は記事の肩書き、`tags` は「経営者・作家・研究者・スポーツ選手・芸能・エンジニア」から合うもの（無ければ空）、`affiliation` は所属がはっきりした経営者と大学教員だけ。`kana` は記事に読みがあるときだけ。
- 新聞社・出版社の社員、書店員、番組スタッフなど、名前で検索されない人は載せない。
- 出力先は `data/research/incoming/YYYY-MM-DD-名前.json`。形は `scripts/import-research.py` の冒頭にある。`checkedUrls` に、使わなかった記事（理由つき）、取得できなかったページ、今回開けなかった候補、見つけた一覧ページを必ず入れさせる。

調査役の報告は鵜呑みにしない。「本文を読んでいない」「断定できない」と書かれた本は、取り込む前に JSON から外す。

## 4. 取り込む

1. `python3 scripts/import-research.py data/research/incoming/ファイル名.json --dry-run` で、足される件数、取り込めない本、食い違いの疑い（`suspects`）を見る。
2. `suspects` が出たら中身を見る。書名の表記の違いだけなら問題ない。別の本が当たっているなら、同じ場所に `ファイル名.pick.json`（`{"書名": null}`）を置いて、その本を外す。取り込んだあとにデータから手で消すだけだと、同じファイルを取り込み直したときに戻ってしまうので、必ず `pick.json` に残す。
3. `--dry-run` を外して取り込む。
4. 取り込めなかった本（`skipped`）は追わない。検索で見つからない本は載せないままでよい。

件数が不自然なとき（1つのファイルで150件を超える、新しい人物が40人を超える）は、取り込まずに報告する。

## 5. 確かめて、本番に出す

1. `pnpm build`（データの検証、ビルド、検索インデックス、ファイル数の確認まで行う）。
2. 落ちたら原因を見る。データの不整合なら直す。直せなければ `git checkout -- data` で取り込み前に戻し、デプロイせずに報告する。
3. ファイル数が 18,000 を超えたという警告が出たら、デプロイはするが、報告の先頭に書く（上限は 20,000）。
4. コミットする。メッセージは `Add recommendations: 出典の概要（N件）`。
5. `pnpm deploy`。
6. 本番で、今回足した人物のページを1つ取得し、200 で名前が出ていることを確かめる。

ソースコード（`src/`、`scripts/`、設定ファイル）は、日次の収集では変更しない。直す必要を見つけたら、`docs/operations.md` のバックログに書いて報告する。

## 6. 記録する

`docs/operations.md` を更新し、コミットする。

- **ログ**: 日付、足した出典と件数、現在の合計（推薦者・本・推薦）を2行以内で足す。
- **継続して見る一覧**: どこまで取り込んだかが変わったら直す。新しい一覧を見つけたら行を足す。
- **ユーザーに依頼中**: ユーザーの判断や作業が要ることを見つけたら足す。

ログが60行を超えたら、30日より前の行を月ごとの要約1行にまとめる。

## 7. 報告する

`discord-notify` スキルで送る。件名は `suisen 収集 M/D`。本文は次の順で、全体を500字以内にする。

1. 足したもの（出典ごとの人数と件数、本番に出たかどうか）
2. 現在の合計（推薦者・本・推薦）
3. 気になった点（外した本、取得できなかった媒体、疑わしい紐付け）
4. お願い（ユーザーの作業が必要なものだけ。無ければ書かない）

失敗や中止のときは、何が起きて、今どういう状態かを先頭に書く。

## やらないこと

- 推薦理由・記事の内容の要約、40字を超える引用。
- 有料記事、書評（薦めたのではなく論評しただけのもの）、第三者のまとめ記事を出典にすること。
- 確かめていない紐付けの掲載。
- ビルドが落ちた状態でのデプロイ。
- 人物 ID の振り直し、既存の人物・本・出典の削除（削除の申し出への対応は、ユーザーの指示があるときだけ）。
- 外部サービスへの投稿、登録、申請、課金。秘密の値の表示やコミット。
- 許可を広げる設定変更（`.claude/settings*.json` の許可リストなど）。
